> A default run gets no temperature information from the climate module. It sets every temperature variable to zero. With `magicc7_ar6`, temperature comes from MAGICC and is refreshed after each iteration.
> 
> ## Default run (`off`)
> 
> `modules/15_climate/off/datainput.gms:53-56` sets these to zero and nothing updates them afterwards:
> - `pm_gmt_conv = 0`
> - `pm_globalMeanTemperature(tall) = 0`
> - `pm_globalMeanTemperatureZeroed1900(tall) = 0`
> - `pm_temperatureImpulseResponseCO2(tall,tall) = 0`
> 
> So `16_downscaleTemperature`, `45_carbonprice`, `50_damages` and `51_internalizeDamages` all see zero warming. Damages that depend on temperature are therefore inactive or trivial, and there is no temperature convergence signal.
> 
> The module does still do two other things (lines 14-50):
> - **Forcing:** it loads exogenous non-CO2 forcing from the RCP file chosen by `cm_rcp_scen`. The default is `rcp45`, which uses `data_oghgf_rcp45.inc`.
> - **Emission caps:** it loads `pm_emicapglob` from files chosen by `cm_rcp_scen` and `cm_multigasscen`.
> 
> ## With `magicc7_ar6`
> 
> The temperature variables are no longer fixed at zero. They are set from MAGICC output in `magicc7_ar6/postsolve.gms`:
> 
> - **Initial value:** `datainput.gms:75` starts `pm_globalMeanTemperature` at 1.
> - **Update:** from iteration 2 on (`iteration.val gt 1`), GAMS dumps `fulldata_postsolve` and runs `Rscript climateAssessmentInterimRun.R`. That script does harmonization, infilling and MAGICC, and takes roughly 2-3 minutes. The postsolve then loads `p15_forc_magicc` and `pm_globalMeanTemperature` from the `p15_climate` file (lines 33-34).
> - **Extension past 2100:** the climate assessment only reports to 2100, so later years are held at the 2100 value (line 37).
> - **Calibration:** if `cm_magicc_calibrateTemperature2000 == "HADCRUT4"`, temperature is shifted so the 2006-2015 mean is 0.97 °C (lines 43-60). This block also computes `pm_gmt_conv` and stores `p15_gmt0` for the next iteration. All 3 scenario configs that select this realization set HADCRUT4. With the default `uncalibrated`, this block is skipped. That also means `pm_gmt_conv` stays at its initial value in that case.
> - **Zeroed at 1900:** `pm_globalMeanTemperatureZeroed1900` is the temperature plus 0.092 (line 64).
> - **Impulse response:** `pm_temperatureImpulseResponseCO2` is only filled if `cm_magicc_temperatureImpulseResponse = on` (default `off`). In that case `climateAssessmentImpulseResponse.R` runs after each of the first 10 iterations and then every fifth. That adds about 10 minutes of runtime according to the code comment. Otherwise it stays zero, so `51_internalizeDamages` gets no marginal-damage signal.
> - **Carbon tax:** if `cm_iterative_target_adj = 2` and `cm_emiscen = 9`, `pm_taxCO2eq` is rescaled between iterations to hit the forcing target. All 3 configs that select this realization set `cm_emiscen = 10` and `cm_iterative_target_adj = 0`, so this branch is not used there.

<details><summary>Answer</summary>

> The carbon removal module (`33_carbonRemoval`, default realization `portfolio`) uses the carbon price in one place. It uses it to cap spending on net negative emissions as a share of regional GDP.
> 
> **Where the price is used:** `q33_carbonRemovalspending` in `modules/33_carbonRemoval/portfolio/equations.gms:313-317`:
> 
> ```
> q33_carbonRemovalspending(t,regi)$(t.val ge max(2035,cm_startyear))..
>   v33_NetNegEmi_expenses(t,regi) =e=
>   (1-cm_frac_NetNegEmi) * pm_taxCO2eqSum(t,regi) * vm_emiAllco2neg(t,regi)
> ```
> 
> - `pm_taxCO2eqSum` is the regional CO2 price. The module gets it from `46_carbonpriceRegi`.
> - `vm_emiAllco2neg` is the net negative emissions variable. It comes from `21_tax`.
> - The equation is only active from 2035 on, or from `cm_startyear` if that is later.
> - `cm_frac_NetNegEmi` is the share of net negative emissions that is left out of the expenses. It is 0.5 by default. Some scenario configs set it to 0 or 0.75.
> 
> **What it limits:** `v33_NetNegEmi_expenses` is the implied monetary value of net negative emissions, meaning price × net negative emissions. The postsolve file puts an upper bound on it in `modules/33_carbonRemoval/portfolio/postsolve.gms:10`:
> 
> ```
> v33_NetNegEmi_expenses.up(t,regi) = p33_GDP_NetNeg_share(regi) * pm_gdp_gdx(t,regi);
> ```
> 
> - The cap is a share of regional GDP, taken from `pm_gdp_gdx`.
> - The share is set by `cm_33_GDP_netNegCDR_maxShare`, which is read in `datainput.gms:148`. The default is 1 globally. That value means 100% of GDP, so the cap rarely binds unless you lower it.
> - The cap is on the carbon-price-weighted value of net negative emissions. It is not a cap on CDR volume.
> 
> The `.up` bound is set in postsolve, so I haven't checked how it is updated between iterations.
